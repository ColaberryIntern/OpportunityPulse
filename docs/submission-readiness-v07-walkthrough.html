Submission Readiness v0.7 (Phase 5 polish)

Dedicated readiness page + vault doc expiry alerts · Walkthrough · 2026-05-08 · commit 81aca1b

Two operationalization upgrades to round out the engine:

  • Dedicated submission-readiness page at /admin/bonfire/:id/submission-readiness — a linkable full-width view per opportunity. More breathing room than the inline drawer; canonical surface for "what's left before I hit Submit?"
  • Vault doc expiry alerts wired into the daily Source Health Agent email. COI expired? 8(a) cert expiring in 12 days? It now shows up red/amber in the same email that already reports source health — instead of failing silently the morning of submission.

No new schema, no new cron — both features piggyback on infrastructure already shipped (the readiness panel from v0.1, the agent email from v9.10). Operational glue, not a new system.

3 · How you get to the page

Two paths, neither destructive:

  1. From the drawer — when you click any row on the /bonfire list, the existing right-side drawer now contains a small grey button beside the original-RFP CTA: 📑 Open full readiness page. Admin only. Opens in the same tab; the drawer closes naturally on navigation.
  2. Direct URL — paste /admin/bonfire/<opportunity-id>/submission-readiness. Useful for emailing teammates a link to a specific bid's status, or linking from a Slack message.

The route is admin-gated server-side and client-side. Non-admins get an "Admin access required." notice instead of the page contents. Same gating story as v0.1 vault.

4 · Vault doc expiry alerts in the daily email

The Source Health Auto-Triage Agent (shipped v9.10) already runs daily after ingest, retries failing sources, classifies remaining failures, and emails the operator only when there's something worth reading. v0.7 extends what counts as "worth reading" to include vault doc expiries:

  • 🚨 Expired (red) — any vault doc whose expires_at is in the past. Listed first; sorted most-expired first.
  • ⏳ Expiring soon (amber) — within 30 days. Sorted closest-to-expiry first.
  • Nothing else — if no docs in either bucket and no source issues, no email. Clean days stay quiet.

The agent loads from documentService.listDocuments({ expiringWithinDays: 30 }), splits by days < 0, and decorates each item with type_label from documentTypes.labelFor() for human-readable subject lines (e.g. Certificate of Insurance (COI) instead of coi).

7 · Email gating logic

The agent only sends if at least one of these is true:

ConditionSource
≥1 source still failing after retryv9.10
≥1 zero-yield source needing manual reviewv9.10
≥1 source auto-recovered (success deserves a mention)v9.10
≥1 vault doc already expiredv0.7
≥1 vault doc expiring within 30 daysv0.7

Otherwise should_email = false and the agent returns silently. Clean days do not page you. See sourceHealthAgent.test.js > "keeps should_email=false when nothing is expired/expiring + nothing else changed".

Important non-behaviors

  • The agent never auto-deletes an expired doc. Expiry is informational; you might still need the file as a historical reference.
  • The agent never auto-renews certifications. Renewal is a human + counterparty workflow (insurance broker, SBA, etc.).
  • The agent never blocks submissions. A bid with an expired COI still generates a package; the package's manifest.json records what was included verbatim.

v0.7.1 · Cloudflare-blocked status (UI honesty)

Discovery: the Fetch from Bonfire button "doesn't work" for most agencies — not because the button is broken, but because Cloudflare blocks the Bonfire detail page on ~80% of portals (HCCS, Round Rock, Richardson, NATO — all return a CF challenge, no attachments). The button completes successfully and the backend logs say "blocked: true," but to the user it just looks like nothing happened.

Before

  • Empty state said "Click ⏬ Fetch from Bonfire to scrape the Documents tab" — implied success.
  • After a blocked fetch, the result toast appeared briefly. On reload, gone — no record of what happened.
  • User: "Did I do something wrong?" → confidence drops on the rest of the readiness UI too.

After

  • Pre-fetch hint now says: "(Cloudflare blocks ~80% of agency portals — don't be surprised if it returns 0.)"
  • After a blocked fetch, the panel persists an amber callout (survives reload):
    ⚠ Cloudflare blocked this portal on the last attempt (12m ago). The Submission Readiness checklist above is a best-effort baseline from the RFP title + description only — it can't read the actual solicitation PDFs. Open the portal manually + verify nothing's missing before submitting.
  • Persistence mechanism: bonfire_opportunities.submission_requirements.last_attachment_fetch = { status, at, blocked }. No new column.
  • If the page parses but lists no documents (different from blocked), shows a neutral grey note: "ℹ No documents listed on the Bonfire detail page."

The 80% block rate is a known limitation of automated Cloudflare bypass on Bonfire — same constraint that affects the existing Phase B/C list scraper. Manual portal navigation remains the fallback.

Cloudflare honesty feedback — phrasing OK? Want a different CTA when blocked (e.g. "Try again," or "Mark as manually fetched")?

v0.7.1 · Baseline vs AI-tailored framing

The deeper question your feedback raised: does the system actually know what the bid needs before downloading the RFP PDFs? Honest answer: partially.

Information availableWhat we can detectWhat we'd miss
Title + description only
(always present; what we have when CF blocks)		 The 6-doc baseline that applies to any government bid (cover letter, capability statement, references, COI, technical response, pricing). Plus regex-based MWBE/DBE detection if the keywords appear in the description. Bonds (bid bond, performance bond), prevailing-wage clauses, EEO certifications, page limits, redacted-vs-public copy requirements, agency-specific forms. These are buried in the PDF body.
+ AI tailoring (no attachments) Same as above; AI may infer additional requirements from richer descriptions. Same gaps — AI is reading the same metadata.
+ AI tailoring (with attachments) Bid-specific requirements quoted from the actual RFP text. Bonds, prevailing-wage notes, EEO clauses, page limits all surface with quoted evidence. Almost nothing — this is the target state.

UI change

The readiness panel header now carries an explicit pill below the % bar:

  • 📋 Baseline — generic checklist for any government bid. CTA: Click 🤖 Tailor with AI to surface bid-specific requirements (bonds, prevailing wage, EEO, etc.).
  • 🤖 AI-tailored (inferred from title + description) — AI ran but didn't have attachment text. Best inference, but limited.
  • 🤖 AI-tailored (read from fetched documents) — AI read the actual RFP. Most accurate; what we want for any bid we'd actually submit.

The badge tells the truth: a 50% readiness on the Baseline track is a different claim than a 50% readiness on the AI-tailored-with-attachments track. Now the user can see which one they're looking at.

Baseline-vs-tailored feedback — does the pill wording capture the distinction clearly?

Final notes

Engine state: with v0.7 shipped, the master plan's Phase 5 is fully operationalized. Recap of what's live end-to-end on Bonfire:

  • v0.1 — Document Vault (30 types, expiry-aware, scope = global | bid)
  • v0.2 — AI requirement tailoring per opportunity
  • v0.3 — AI-generated docs, dual-write to bid + global with shared lineage
  • v0.4 — RFP attachment locker (Bonfire detail-page scrape, Cloudflare-aware)
  • v0.5 — One-click submission package ZIP (vault docs + AI drafts as PDF + RFP attachments + README + manifest)
  • v0.6 — Auto-fill from vault excerpts in proposal/offer/resume generation, with audit trail
  • v0.7 — Dedicated readiness page + vault expiry alerts in daily email

What's left from the original master plan:

  • SAM.gov + grants.gov per-opportunity attachment fetchers (~14h). Same shape as the v0.4 Bonfire fetcher, but the platform-specific scrapers don't exist yet — SAM.gov has a paid API tier with attachment URLs and a free tier that requires HTML scraping; grants.gov has a public synopsis API. Note: SAM/grants.gov do not have the same Cloudflare problem Bonfire does, so attachment fetching there should generally work.
